# SAÑLAQ Character Art Brief — Body & Clothing Repaint

## Why this document exists instead of new PNGs

This session was asked to raise the character/clothing art from placeholder to the
target "soft stylized 2D cartoon" style (project brief §11). No image-generation
tool or MCP was available in this environment (checked and confirmed empty) to
actually paint the sprites. Hand-drawing the replacement pixel-by-pixel in this
session would just produce a different flavor of the same problem the task is
trying to fix — §11 explicitly rules out pixel art, and rushed procedural
rectangles would not read as real garments either. So instead of guessing, this
brief specifies exactly what to paint, at what size, aligned to what pivot, in
what palette, so the result drops into the existing pipeline with zero code
changes. Hand this to an illustrator, an image-gen tool, or a future session that
has one.

**Nothing in code, scenes, or data was touched this session.** This is analysis +
spec only, per the task's own fallback instruction.

## Current state (confirmed by inspection)

`assets/character/**/*.png` are generated by `tools/generate_character.py`: flat
16×16-logical rectangles (a torso is literally one filled box, a hat is a smaller
box on top of the head box) upscaled 4× with nearest-neighbor filtering. Every
garment in [head_saukele_01.png](head/head_saukele_01.png),
[torso_shapan_01.png](torso/torso_shapan_01.png),
[shoes_saptama_etik_01.png](shoes/shoes_saptama_etik_01.png), etc. is an abstract
colored block, not a recognizable Kazakh garment — confirmed by opening the
sheets directly. This is the "programmer art" the task refers to, and it violates
§11 ("no pixel art") outright, independent of the recognizability problem.

The project also already has real reference photos for every item at
`assets/ui/encyclopedia_photos/*.jpg` (credited in `CREDITS.md`), which are a
better silhouette reference than anything I'd generate from memory — use them.

## Non-negotiable technical constraints (from the actual code)

Read [character_visual.gd](../../scripts/entities/character_visual.gd) and
[character_visual.tscn](../../scenes/entities/character_visual.tscn) before
painting anything. They define a hard contract new art must satisfy:

1. **Sheet layout is fixed.** One PNG per item, **384×256px**, laid out as **4
   rows × 6 columns of 64×64 frames**. Rows = `down, up, left, right` (in that
   exact order). Columns = `idle0, idle1, walk0, walk1, walk2, walk3`. This is
   read directly by `_build_frames()` via hardcoded `Rect2(col*64, row*64, 64,
   64)` — do not change the grid, frame count, or frame size.
2. **`right` is a full row in the file, not a runtime mirror.** The current
   generator builds the `left` pose and horizontally flips it into the `right`
   row at export time (`build_sheet()`); the game code just reads row 3
   literally. So: paint/generate `down`, `up`, `left` (18 frames), then flip the
   `left` row horizontally into the `right` row before exporting. Do this
   identically for every layer so flipped clothing still lines up with the
   flipped body.
3. **Idle frames can be near-duplicates.** `character_visual.gd` already adds a
   procedural vertical bob to the whole node in `_process()` (`_pose_time`
   sine bounce), independent of which frame is showing. Idle0/idle1 don't need
   to carry the "breathing" motion themselves — a static pose (or a 1px
   blink/chest-rise) is enough. Spend the art budget on the 4 walk frames per
   direction, which do need a real contact–pass–contact–pass leg cycle.
4. **All 5 layers must share one pose skeleton, per frame, per direction.**
   `CharacterVisual` stacks `Base → Shoes → Pants → Torso → Head` as five
   independent `AnimatedSprite2D`s at the same node position, frame-synced by
   index (`_process()` sets `.frame = f` on every layer at once). There is no
   per-layer offset. If the torso sheet's frame `left/walk2` puts the shoulders
   1px off from the base body sheet's `left/walk2`, clothing will visibly float
   or clip on every left-walking frame. **Practical method:** finalize the 3
   body poses first (all 24 frames × 3 skin variants), then for every garment
   sheet, keep the matching body frame as a locked, half-opacity reference layer
   underneath while painting, and delete that reference layer only at export.
5. **Character fills nearly the full 64×64 cell.** In the current logical
   grid the figure spans roughly the full 16-unit height (head top ≈ row 0,
   feet ≈ row 16) and is horizontally centered, about 10 of 16 units wide at
   the shoulders/arms. Keep that framing — `AnimatedSprite2D` is centered by
   default, and downstream code (catch-radius ring, bounce) assumes the figure
   is centered with feet near the bottom edge, not padded with empty margin.
6. **Filenames and paths are load-bearing — do not rename anything.**
   `character_visual.gd` hardcodes `BASE_SHEETS` to the three `base*.png`
   paths; every `data/clothing/*.tres` hardcodes `texture_path` /`icon_path` to
   the exact current filenames. New art replaces these files in place, same
   name, same folder.
7. **Z-order matters for silhouette design.** Draw order is Base < Shoes <
   Pants < Torso < Head. A long garment (shapan, koylek) is expected to
   visually cover the top of the legs — the current generator already models
   this via an extra hem rectangle over the torso's z-layer — keep that: hems
   render over pants, not under.
8. **Texture import is currently pixel-art (nearest) filtering**
   (`textures/canvas_textures/default_texture_filter=0` in `project.godot`,
   and each `*.png.import` has no smoothing override). Soft cartoon art will
   look wrong with nearest filtering — when real art lands, give the character
   PNGs a per-file import override to `Filter: On` (or switch just those
   `.import` files), rather than changing the global project default, which
   would also affect any tile art that's intentionally staying pixel-crisp.
   Not done in this session — flagged for whoever integrates the final art.

## Paint resolution

Painting straight at 64×64 with hard-edged fills is exactly the pixel-art look
the brief prohibits. Paint each frame considerably larger (e.g. a 256×256 or
512×512 working canvas per frame, or a vector illustration) with soft
anti-aliased edges and flat cel-shading, then downsample the whole sheet to the
final 384×256 with a high-quality (Lanczos/bicubic) filter — not nearest
neighbor. The exported file must still be exactly 384×256 with frames on exact
64px boundaries; only the interior linework changes from blocky to smooth.

## Global style guardrails (project §11 / §12 / §29)

- Soft stylized 2D cartoon: rounded shapes, clean 2–3px (at final 64px scale)
  outline of consistent weight on every layer — an outline that's 1px on the
  body and 3px on a hat reads as mismatched art styles.
- Flat cel-shading only: a base tone + one soft shadow tone per color. No
  gradients, no glow, no rim light, no drop shadows baked into the sprite.
- Silhouette-first: every garment must be identifiable filled-in solid black,
  at 64×64, before any interior detail is added. If two headwear items look
  the same in silhouette, differentiate the *shape*, not just the color.
- One consistent "camera": top-down, 4-direction stance — `down` reads as a
  3/4-front face, `up` shows the back of the head/hair with no face, `left`
  is a clean side profile (`right` is its mirror). Every layer must obey the
  same implied camera angle; don't let one garment look front-on while
  another looks isometric.
- No photorealistic texture, no fabric-weave noise, no busy embroidery
  micro-detail that will just dither into mush at 64px — pick **one** accent
  motif per garment (a trim line, a chest panel, a band) and keep it bold.
- Avoid neon; stay inside the palette below.

## Body (3 variants — `base/base.png`, `base_02.png`, `base_03.png`)

Friendly Kazakh boy, roughly 10–15, cartoon "big head" proportions (head ≈ 30%
of total figure height, matching the current rig's frame layout — do not shrink
the head to realistic proportions, it will look wrong stacked with the same
garment sheets). Simple face: two small dot/oval eyes, a soft smile line, no
nose or a single tiny dash. No visible ears needed under headwear.

- **base.png** — skin `#F4DBB2`, short simple combed hair `#483222`, neutral
  friendly expression. This is the default/most-used variant — give it the
  clearest, simplest read since it's seen most.
- **base_02.png** — skin `#CA8B5B`, hair `#281D19` styled as a small single
  back braid (subtle — a young boy's braid, not an elaborate one), slightly
  more playful/confident expression.
- **base_03.png** — skin `#E7B985`, hair `#6C3F1F` with a simple side-swept
  fringe, cheerful expression.

All three must present clean, ungapped seams at wrists, neck, waist and ankles
so every garment/shoe/hat sits flush with no bare-skin sliver at the edges.

## Headwear (`head/`, slot_type HEAD) — most gameplay-critical set

These are what the catcher has to identify, so silhouette separation between
all five matters more here than anywhere else:

- **head_borik_01 — Бөрік** (`#9C6437` fur, `#EAC25B` accent). Round hat with
  a thick fur band wrapping the head (textured, not flat — small tufted
  strokes) and a softly domed fabric/fur crown above it. No flaps. Reference:
  [borik.jpg](../ui/encyclopedia_photos/borik.jpg).
- **head_takiya_01 — Тақия** (`#9E2222` base, `#EAC25B` accent). Small stiff
  four-panel skullcap, sits close to the head, no brim, no flaps, small gold
  motif at the crown apex. Deliberately the lowest-profile, smallest silhouette
  of the set — must read as clearly smaller/flatter than borik/tymaq/saukele.
- **head_saukele_01 — Сәукеле** (`#9C2836` base, `#FCE1A3` gold ornament).
  Tall narrow cone rising well above the head, fur/fabric band at the base,
  gold banding around the cone, a small feather/pompom tuft at the tip that
  sways 1–2px side to side across the walk frames (this animated sway already
  exists in the current generator's logic — preserve the idea). Reference:
  [saukele.jpg](../ui/encyclopedia_photos/saukele.jpg) (re-key magenta → the
  game's red/gold). Signature read: unmistakable height — tallest headwear
  by a wide margin.
- **head_tymaq_01 — Тымақ** (`#9C6437` fur). Rounder fur-textured crown plus
  two ear-flaps hanging down past the jawline on each side, drawn as clearly
  separate dangling shapes (not tucked/flat) — the flaps are what
  distinguishes it from borik. Reference:
  [tymaq.jpg](../ui/encyclopedia_photos/tymaq.jpg).
- **head_kimeshek_01 — Кимешек** (`#E8E6E0` cream, thin navy or gold trim at
  the face opening). White/cream fabric hood that wraps the head *and*
  drapes down over the neck and shoulders — the only headwear that covers
  the neck, and the only pale/cloth one (versus four fur/velvet hats). Its
  silhouette must read as soft draped cloth, not a rigid fur volume.

## Footwear (`shoes/`, slot_type SHOES)

- **shoes_masi_01 — Мәсі** (`#4A301C`). Soft low-cut leather ankle boot,
  rounded toe, minimal seams — the plainest, lowest silhouette of the three.
- **shoes_kebis_01 — Кебіс** (`#6A5234` base, `#EAC25B` accent). Worn over
  masi: same low-ankle height but a visibly thicker/chunkier sole band and a
  slightly stiffer cuff. The extra sole thickness is the one differentiator
  from masi at small scale.
- **shoes_saptama_etik_01 — Саптама етік** (`#2C2C30`). Tall riding boots —
  shaft rises well above the ankle toward where the pant hem sits, clearly
  taller than masi/kebis, plain dark leather, small heel. Height alone must
  sell the difference.

## Icon previews

`assets/items/<id>.png` (128×128, one static pose, currently `down`/`idle0`
cropped and upscaled by the same generator) needs the same treatment per item —
either export a clean `down`/idle frame from the new sheet at higher source
resolution and downsize to 128×128, or paint a dedicated higher-detail
128×128 icon per item. Not required for in-game correctness (the game only
reads `texture_path`, not `icon_path`, during play) but used by the
quiz/wardrobe UI, so it should ship alongside the sheet, not be skipped.

## Scope note: variant counts

The task asked for "5 variants each" per §10's target. Current data
(`data/clothing/*.tres`) only defines **3 torso, 2 pants, 5 head, 3 shoes**
items (plus 3 body skins). This brief covers repainting exactly what exists
today at real fidelity. Reaching 5/5/5/5 requires *new* `ClothingItem`
resources (2 more torso, 3 more pants, 2 more shoes — new IDs, new
`wrong_answers_kz`, new encyclopedia photos, etc.), which is a content-design
task, not just an art task, and out of scope for a pure visual-fidelity pass.
Flagging it as a separate follow-up rather than silently expanding the data
files.

## What still needs manual art review once real sprites exist

1. Actually painting/generating the 16 sheets (3 body + 13 garments) per this
   spec, in an environment with image-gen access, or by an illustrator.
2. Re-cropping/repainting the 13 `assets/items/*.png` icon previews.
3. Per-file Godot import override to `Filter: On` for the new character
   textures (leave the project-wide nearest-filter default alone).
4. In-editor playtest: run `game.tscn`, walk in all 4 directions with each
   clothing combination equipped, confirm no seam gaps/clipping between
   layers frame-by-frame (this is the failure mode most likely to slip
   through a static review — it only shows up mid-animation).
5. A silhouette pass: screenshot each headwear item at actual in-game catch
   distance (~56px, per the 28px catch radius) and confirm a human can still
   tell them apart without color, since that's the literal gameplay
   mechanic (§2).
