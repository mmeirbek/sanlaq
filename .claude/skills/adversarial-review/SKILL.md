# Adversarial Review

Когда Claude проверяет код, который сам написал или только что прочитал, у него та же картина в голове, что у автора, и те же слепые пятна. Отсюда «выглядит хорошо» на коде, который свежий человек забраковал бы сразу. Этот скилл заставляет сменить точку зрения.

## Что проверять

- Без аргумента: `git diff` + `git diff --cached`; если пусто — `git diff HEAD~1`.
- `--diff <ref>`: `git diff <ref>`. Для PR этапа: `git diff main...HEAD`.
- `--file <path>`: весь файл целиком.

Нечего проверять — так и сказать.

## Порядок

1. **Полный контекст.** Каждый файл из диффа читается целиком: баги живут на стыке нового и старого кода. Определить тип правки: багфикс, фича, визуал, рефакторинг, тест.
2. **Правила проекта.** `CLAUDE.md` и раздел «Правила работы» в `docs/REDESIGN_PLAN.md`.
3. **Три роли по очереди.** Каждая **обязана** найти хотя бы одну проблему. Не нашла — значит, плохо смотрела. Если код правда безупречен, назвать самое хрупкое допущение, на котором он держится.
4. **Свести.** Объединить дубли. Находку, которую поймали 2+ роли, поднять на уровень выше.

Не смягчать. Не «возможно, это мелочь, но…». Либо проблема, либо нет.

## Роль 1. Саботажник

«Я хочу сломать это в игре у живого игрока».

- Таймеры и `await`: что если сцена уже сменилась, узел освобождён, таймер пережил следующее событие?
- Сигналы: подключены дважды? не отключены при выходе? срабатывают после `queue_free`?
- Состояние матча: что если событие придёт дважды, в одном кадре, во время паузы, после конца матча?
- Зависимость от кадра: логика в `_process` без `delta`, разное поведение при 30 и 144 FPS.
- Размеры: раскладка на 1280×720, 1560×720 (телефон), 960×720 (планшет); сенсорный ввод.
- Web-сборка: файлы, которые не попадут в экспорт; звук до первого касания.
- Пограничный ввод: пустой список, ничья, одна карточка, выход посреди партии.

Для каждой изменённой функции спросить: худший вход? что если вызвать дважды? ни разу? из другого режима?

## Роль 2. Новичок

«Я пришёл в команду и через полгода должен поменять этот код без автора».

- Имена, которые не говорят, что делают (`data`, `process()`, `tmp`).
- Магические числа и строки вместо констант; роли и состояния строками вместо `enum`.
- Глубокие пути к узлам вместо `%UniqueName`.
- Стили, собранные вручную, вместо темы и type variations.
- Видимый текст без `tr()` — сломает локализацию kk/en.
- Нет аннотаций типов там, где их ждёшь.
- Функция делает больше, чем говорит имя.
- Расходится со стилем соседнего кода.
- Тест проверяет реализацию, а не поведение; новый код без теста — **всегда** находка.

## Роль 3. Аудитор данных

«Этот код будет у тысяч игроков, а их данные — у нас».

- **Сохранения** (`SaveManager`, `user://save_data.json`): старое сохранение без нового поля, битый JSON, потеря прогресса при обновлении.
- **Телеметрия и лицензирование станций** (`autoload/telemetry.gd`): что уходит наружу, нет ли лишних данных об игроке, что при отсутствии сети, можно ли обойти лимит устройств.
- **Секреты:** ключи, токены, URL с доступом в коде, конфигах, комментариях.
- **Тесты и CI** не должны трогать настоящее сохранение игрока и слать телеметрию.
- **CI/CD** (`.github/workflows/`): деплой только после зелёных тестов, права минимальные.

## Редизайн: обязательные проверки

- Механика не изменилась в «визуальном» коммите. Если задета — это отдельный коммит с тестом.
- Новые ассеты — только из `tools/artgen` или одобренный импорт; палитра и масштаб — по правилам плана.
- Старый ассет удалён, если больше не используется.

## Уровни

| Уровень | Что это | Что делать |
|---|---|---|
| **CRITICAL** | Потеря сохранения, сломанный режим, падение, утечка данных, сломанный деплой | Блокирует слияние |
| **WARNING** | Баг на краях, тормоза, путаница для следующего разработчика | Исправить или явно принять риск с причиной |
| **NOTE** | Стиль, мелкое улучшение, документация | На усмотрение автора |

## Ответ

```markdown
## Adversarial Review: [что проверяли]

**Объём:** [файлы, строк, тип правки]
**Вердикт:** BLOCK / CONCERNS / CLEAN

### Critical
### Warnings
### Notes

### Итог
[2–3 предложения: общий риск и самое важное, что исправить.]
```

- **BLOCK** — есть CRITICAL. Не сливать.
- **CONCERNS** — критических нет, но 2+ WARNING. Слияние на свой риск.
- **CLEAN** — только NOTE.

## Как сломать «самоодобрение»

1. Читать снизу вверх, с последней функции.
2. Перед чтением тела функции сформулировать её контракт. Тело ему соответствует?
3. Считать каждую переменную `null`, пока не доказано обратное.
4. Считать, что каждый внешний вызов упадёт.
5. «Если удалить эту правку целиком, что сломается?» Если ничего — правка, может, и не нужна.

## Чего не делать

- «LGTM, проблем нет».
- Только косметика при пропущенном `null`.
- Пересказ диффа вместо находок.
- Ревью только изменённых строк.
