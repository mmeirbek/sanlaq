# Handoff

Написать документ передачи, по которому новая сессия продолжит работу. Сохранить в `.claude/handoffs/<ГГГГ-ММ-ДД>-<кратко>.md` (папка в `.gitignore`). Перед записью проверить, нет ли уже файла с таким именем.

Если пользователь передал аргумент — это цель следующей сессии, документ подстраивается под неё.

**Главное правило: не дублировать.** Что уже есть в плане (`docs/REDESIGN_PLAN.md`), спецификациях режимов, коммитах, PR и коде — давать ссылкой (путь, `file:line`, SHA, номер PR), а не пересказом.

## Разделы

### 1. Цель следующей сессии

2–3 предложения: какой результат она должна получить. Плохо: «продолжить работу». Хорошо: «Закрыть пункт 0.5 плана: `tools/screenshot_screens.gd` снимает все экраны в 3 размерах; открыть PR из `redesign/0-foundation`».

### 2. Состояние

- **Готово:** пункты со ссылками (пункт плана, коммит).
- **В работе:** ветка, последний коммит, файл, где остановились.
- **Блокирует:** что и кто разблокирует.

Конкретно: не «рефакторинг HUD», а «`redesign/4-hud`, коммит `abc1234`, падает `smoke_test`».

### 3. Открытые решения

Только то, что следующая сессия **должна** решить: варианты, к чему склоняется пользователь, от чего зависит.

### 4. Скиллы для следующей сессии

Конкретно, например:
- `red-green-proof` — для бага X;
- `grill-me` — по спецификации Y до начала кода;
- `adversarial-review` — перед слиянием PR в `main`.

### 5. Ссылки (только ссылки)

План, спецификации, ветка, PR, свежие коммиты, результат последнего прогона тестов (`tools/run_tests.sh`: зелёный/какие упали).

## Что не включать

- Пересказ плана или спецификации — ссылка.
- Код длиннее пары строк — `file:line` и SHA.
- Историю переписки.
- То, что уже записано в коммитах.

Хороший документ — 30–80 строк. Длиннее — значит, что-то дублируется.

Перед сохранением проверить, что ветки и пути из документа существуют (`git branch`, `ls`).
